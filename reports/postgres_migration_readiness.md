## Blockers

- ~1032 literal `?` placeholders in scoped core modules — requires `db_param_placeholder()` / `db_placeholders()` rollout (primary SQL blocker after identity work)
- SQLite-only schema ensure (`AUTOINCREMENT`, `PRAGMA`) — no Postgres DDL bootstrap path

## High Risk

- PRAGMA usage (1442 refs) — schema introspection must use information_schema on Postgres
- sqlite_master queries (55 refs) — replace with information_schema / pg_catalog

## Medium Risk

- 42 tables use AUTOINCREMENT — map to SERIAL/IDENTITY in Postgres DDL
- INSERT OR IGNORE — partially covered by db_insert_ignore_sql(); audit all call sites
- Dual reporting (financials.py vs accounting_engine) — verify branch filters on Postgres

## Low Risk

- GLOB patterns — use Postgres ~ or SIMILAR TO / regex
- INTEGER booleans (0/1) — use db_boolean_value() or native BOOLEAN

## Migration Recommendation

1. Complete Phase 5B data cleanup on SQLite (POS branch_id, managers, payment reference).
2. Finish **placeholder** migration on critical read/write paths using `database.db_placeholders()` (identity on critical INSERTs is largely complete per Phase 5B.10).
3. Generate Postgres DDL from SQLite schema (AUTOINCREMENT → GENERATED BY DEFAULT AS IDENTITY).
4. Run read-only FK orphan remediation on SQLite before cutover.
5. Enable `DB_BACKEND=postgres`, `DATABASE_URL`, `ERP_ENABLE_POSTGRES_RUNTIME=1` only in staging first.
6. Do **not** switch production `DB_BACKEND` until regression + concurrency tests pass on Postgres.

**Do not migrate data in this phase.**
