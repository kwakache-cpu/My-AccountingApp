# PostgreSQL Schema Deployment Plan

Phase: 5B.13C  
Status: design plus Phase 5B.13D introspection infrastructure, Phase 5B.13E offline DDL generation, and Phase 5B.13F offline schema validation. No data migration, Supabase deployment, production runtime enablement, or PostgreSQL schema deployment is included.

## Executive Summary

The Phase 5B.13B startup gate now prevents enabled PostgreSQL runtime from entering SQLite-only schema/recovery paths. The next hard blocker is a PostgreSQL-native schema deployment path. Current schema ownership is split across `database.py` bootstrap functions, `ensure_schema_integrity()`, `_deploy_full_schema()`, runtime self-heal helpers, and `erp_migrations.py`; those paths use SQLite DDL, `PRAGMA table_info`, `sqlite_master`, `AUTOINCREMENT`, and `INSERT OR IGNORE`.

The PostgreSQL target should be a deterministic initial schema deployer that creates tables, constraints, indexes, migration metadata, and seed data without touching SQLite runtime data. It should not reuse SQLite DDL strings directly.

Phase 5B.13D update: backend-aware schema introspection helpers now exist for tables, columns, indexes, and foreign keys. Low-risk diagnostics/readiness metadata callers use the abstraction. SQLite schema deployment/self-heal paths remain SQLite-native, and PostgreSQL DDL deployment is still not implemented.

Phase 5B.13E update: `postgres_schema_generator.py` now generates offline PostgreSQL DDL draft artifacts from the schema compatibility inventory:

- `reports/postgres_generated_schema.sql`
- `reports/postgres_generated_schema_summary.md`

The generator captures all 51 SQLite tables, 67 indexes, and 47 foreign keys from the inventory report. It does not connect to any database and does not deploy schema.

Phase 5B.13F update: `postgres_schema_validator.py` now validates the generated schema artifacts offline and writes `reports/postgres_schema_validation_report.md`. Current validation result is 90/100 with **YELLOW** deployment readiness: 51/51 tables represented, required core tables present, primary keys present, 67 indexes captured, 47 foreign keys captured, and no forbidden SQLite syntax in generated SQL. Manual review and unsupported-source construct items remain, and deployment is still not implemented.

Phase 5B.15B update: `reports/sqlite_postgres_schema_mismatch_review.md` compares the live SQLite schema shape to the generated PostgreSQL schema before any row-copy work. The current review finds 47 live SQLite columns with no generated PostgreSQL target column, concentrated in `cashier_closings`, `pos_returns`, `pos_sales`, and `pos_suspended_sales`. All 47 are classified **BLOCKER** for data migration dry-run row mapping until the PostgreSQL schema plan is reconciled.

## Target DDL Strategy

Use a declarative PostgreSQL schema manifest as the source for deployment. The manifest should define tables, columns, primary keys, foreign keys, unique constraints, indexes, and seed rows in structured Python data or SQL files. The deployment command should compile that manifest into PostgreSQL DDL and execute it only against an explicit staging database.

Recommended strategy:

1. Keep SQLite schema bootstrap unchanged for normal production.
2. Add PostgreSQL-specific schema definitions outside the SQLite self-heal path.
3. Create all base tables in dependency order.
4. Add primary keys and inline unique constraints during table creation where possible.
5. Add foreign keys after all parent tables exist when dependency ordering is complex.
6. Add indexes after table creation.
7. Insert seed data with `ON CONFLICT DO NOTHING`.
8. Record deployment in a PostgreSQL migration history table.
9. Run validation queries before PostgreSQL startup gate can be relaxed.

Do not deploy schema from `ensure_schema_integrity()` or `_deploy_full_schema()` directly. Those functions remain SQLite-native until deliberately refactored.

## Type Mapping

| SQLite Pattern | PostgreSQL Target | Notes |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | Use for surrogate numeric IDs. Keep natural text keys such as `companies.key`, `branches.branch_id`, and `database_identity.instance_id` as text primary keys. |
| `INTEGER PRIMARY KEY` for singleton/config rows | `INTEGER PRIMARY KEY` | Keep for `system_settings.id`, `schema_version.version`, and similar fixed IDs unless identity behavior is required. |
| `INTEGER` FK to identity PK | `BIGINT` | Match parent identity key type. |
| `INTEGER` count/quantity fields | `INTEGER` or `BIGINT` | Use `INTEGER` for small counts and `BIGINT` for row IDs/counts that may grow. |
| `INTEGER DEFAULT 0/1` flags | `BOOLEAN DEFAULT false/true` where safe | Safe for columns used as booleans such as `is_active`, `is_locked`, `is_voided`, `posting_allowed`, `control_account`, `allow_manual_posting`, `opening_posted`. Keep numeric fields numeric when they represent counts or quantities. |
| `REAL` money/amount fields | `NUMERIC(18,2)` | Use for prices, amounts, totals, balances, costs, salaries, taxes, rates that represent money. |
| `REAL` quantities/rates | `NUMERIC(18,4)` or `NUMERIC(12,4)` | Use for inventory quantity, tax rate, depreciation rate, exchange rate, useful life, and non-money measures. |
| `TEXT` free text | `TEXT` | Keep for descriptions, names, notes, JSON text until JSONB conversion is planned. |
| JSON stored as `TEXT` | `JSONB` where safe, otherwise `TEXT` | Candidate columns: `metadata_json`, `features_json`, `cart_json`, `recurrence_payload`, row-count snapshots. Convert only after callers are audited. |
| `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` | `TIMESTAMPTZ DEFAULT now()` | Use for created/updated/posted/approved timestamps where timezone awareness is safe. |
| `TEXT` timestamp fields | `TIMESTAMPTZ` where safe | Candidate columns ending in `_at`, plus `created_at`, `updated_at`, `paid_at`, `verified_at`, `activated_at`. |
| `TEXT` date fields | `DATE` where safe | Candidate columns ending in `_date`, accounting periods, invoice/bill/payment dates, closing dates, next run dates. Preserve `TEXT` only when mixed date/string values are expected. |
| `DATETIME` | `TIMESTAMPTZ` | Normalize to one timestamp type. |
| `UNIQUE(...)` | `UNIQUE (...)` | Preserve existing uniqueness, preferably named constraints. |
| `INSERT OR IGNORE` | `INSERT ... ON CONFLICT (...) DO NOTHING` | Conflict target must be explicit and backed by a unique/primary key constraint. |
| `CURRENT_TIMESTAMP` | `now()` or `CURRENT_TIMESTAMP` | Prefer `now()` in generated PostgreSQL DDL for consistency. |
| `PRAGMA table_info` | `information_schema.columns` / `pg_catalog` | Use backend-aware introspection helpers. |
| `sqlite_master` | `information_schema.tables` / `pg_catalog.pg_class` | Use backend-aware table existence helpers. |
| SQLite `?` placeholders | `%s` with psycopg/psycopg2 | Use existing portable query/write helpers or PostgreSQL-specific SQL. |

## SQLite-to-PostgreSQL Pattern Map

| Current Pattern | PostgreSQL Plan |
|---|---|
| `AUTOINCREMENT` | Replace with `BIGINT GENERATED BY DEFAULT AS IDENTITY`. Validate sequence ownership and allow explicit ID insert during data migration if needed. |
| `CURRENT_TIMESTAMP` | Use `now()` defaults for `TIMESTAMPTZ`; use explicit `DATE` defaults only where business rules require them. |
| `DEFAULT 0/1` | Convert to booleans only for semantic flags. Keep numeric defaults for counts, money, quantities, and status codes. |
| `UNIQUE` | Preserve as named constraints. All `ON CONFLICT` seed statements must target these constraints. |
| `ON CONFLICT` | Use PostgreSQL `ON CONFLICT (columns) DO NOTHING` or `DO UPDATE` only after the unique index/constraint exists. |
| `INSERT OR IGNORE` | Convert branch type seeds, module defaults, migration records, singleton settings, and idempotent users to explicit `ON CONFLICT`. |
| `PRAGMA table_info` | Replace with `db_column_exists()` PostgreSQL branch or direct `information_schema.columns`. |
| `sqlite_master` | Replace with `db_table_exists()` PostgreSQL branch or direct `information_schema.tables`. |
| `TEXT date handling` | Convert operational date columns to `DATE`; convert timestamp audit columns to `TIMESTAMPTZ`; update query filters away from SQLite `strftime`. |

## Core Table Plan

### Identity And Natural Keys

Use natural text primary keys where already established:

- `companies.key`
- `branches.branch_id`
- `branch_type_catalog.branch_type_key`
- `database_identity.instance_id`
- `migration_history.migration_id`
- `schema_version.version`

Use identity `BIGINT` for surrogate IDs on operational rows:

- Accounting/documents: `journal_entries`, `journal_lines`, `invoices`, `bills`, `payments`, `payment_allocations`, `vouchers`, `transactions`
- Master data: `customers`, `suppliers`, `inventory`, `chart_of_accounts`, `bank_accounts`, `counterparties`
- POS: `pos_sales`, `pos_sale_lines`, `pos_returns`, `pos_suspended_sales`, `cashier_closings`
- Branch licensing: `branch_type_module_defaults`, `branch_module_grants`
- Audit/system: `audit_logs`, `system_logs`, `migration_logs`

### Foreign Keys

Preserve the current FK intent:

- Child tables with `company_key` reference `companies(key)`.
- Branch-scoped tables with `branch_id` reference `branches(branch_id)`.
- Document line tables reference parent document headers with `ON DELETE CASCADE`.
- `journal_lines.entry_id` references `journal_entries(id)` with `ON DELETE CASCADE`.
- `journal_lines.account_id` references `chart_of_accounts(id)`.
- `stock_movements.inventory_item_id` references `inventory(id)`.
- `payments.bank_account_id` references `bank_accounts(id)`.
- `payment_allocations` references `payments`, `invoices`, `bills`, `branches`, and `companies`.
- POS lines reference `pos_sales`; POS sales/returns/suspended sales reference `companies`.

Use `ON DELETE CASCADE` where current SQLite DDL does. Use `ON DELETE SET NULL` for optional branch/inventory references that currently use it. Avoid adding stricter FK behavior until data migration validation confirms there are no orphaned rows.

### Indexes

## Deployment Phases

### A. Backend-Aware Schema Introspection Helpers

Status: implemented in Phase 5B.13D for shared helper infrastructure and low-risk diagnostics/readiness callers.

Objective: provide safe table/column/index/constraint existence checks for PostgreSQL without `PRAGMA` or `sqlite_master`.

Files likely touched: `database.py`, `erp_migrations.py`, tests.

Risks: inconsistent metadata results between SQLite and PostgreSQL; unsafe identifier interpolation; schema search path ambiguity.

Required tests:

- PostgreSQL SQL generation for table existence uses `information_schema`.
- Column existence helper emits `%s` placeholders.
- SQLite helper behavior remains unchanged.
- No helper returns or logs full `DATABASE_URL`.

### B. PostgreSQL DDL Generator

Status: implemented in Phase 5B.13E as an offline generator only. Generated SQL remains a draft artifact requiring manual review before any future deployer can use it.

### B2. PostgreSQL Schema Validator

Status: implemented in Phase 5B.13F as an offline validator only. It checks generated SQL coverage against the schema compatibility inventory and reports forbidden SQLite syntax, missing required tables, missing primary keys, FK/index counts, unsupported-source construct count, and manual review count. It does not connect to PostgreSQL or deploy schema.

Objective: compile a structured schema manifest into PostgreSQL `CREATE TABLE`, constraints, indexes, and seed statements.

Files likely touched: new schema manifest module or SQL files, `database.py`, tests.

Risks: type mismatches, unsafe quoting, missing defaults, identity columns not matching data migration needs.

Required tests:

- DDL generation snapshot tests for representative tables.
- Identity mapping test: `AUTOINCREMENT` equivalent becomes `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Boolean/money/date/timestamp mapping tests.
- Constraint/index generation tests.

### C. PostgreSQL Initial Schema Deployer

Objective: create an empty PostgreSQL schema in staging only, behind explicit command/flag, without enabling app runtime.

Files likely touched: `database.py`, optional deployment script/CLI, tests.

Risks: accidental production execution, partial deployment, schema drift from SQLite source, search path mistakes.

Required tests:

- Deployer refuses to run unless `DB_BACKEND=postgres`, `DATABASE_URL` is set, runtime/deploy flag is explicit, and environment is staging.
- Deployer runs in a transaction or records partial failure safely.
- SQLite startup tests unchanged.

### D. PostgreSQL Migration History Table

Objective: create PostgreSQL-native `schema_version`, `migration_history`, and `migration_logs` tables.

Files likely touched: `database.py`, `erp_migrations.py`, tests.

Risks: divergent migration version semantics, `INSERT OR IGNORE` conversion mistakes, identity mismatch in `migration_logs`.

Required tests:

- `migration_history(migration_id)` primary key supports `ON CONFLICT (migration_id) DO NOTHING`.
- `schema_version(version)` records current version.
- `migration_logs.id` uses identity.

### E. PostgreSQL Seed Data Deployment

Objective: seed default chart of accounts, branch type catalog, branch module defaults, singleton system settings, and any required plan settings idempotently.

Files likely touched: `database.py`, seed manifest, tests.

Risks: missing unique constraints for conflict targets; duplicate seeds; seed data drift from SQLite bootstrap.

Required tests:

- Running seeds twice is idempotent.
- `branch_type_catalog` contains expected catalog keys.
- `branch_type_module_defaults` contains templates.
- `system_settings` singleton exists.
- Seed statements do not use `INSERT OR IGNORE`.

### F. PostgreSQL Staging Deployment Command

Objective: provide an explicit non-production command to deploy schema to a staging PostgreSQL database.

Files likely touched: new script/CLI, documentation, tests.

Risks: accidental Supabase production deployment, wrong database URL, missing SSL, partial DDL.

Required tests:

- Command requires a staging confirmation flag.
- Command refuses production runtime unless explicitly allowed by a future phase.
- Command redacts URL in logs.
- Dry-run emits DDL without connecting.

### G. PostgreSQL Validation Checks

Objective: validate deployed schema before relaxing the startup gate.

Files likely touched: `database.py`, validation script/report, tests.

Risks: false green from incomplete checks; missed indexes/constraints; no seed validation.

Required tests:

- Required table count and required table names.
- Required columns and mapped types.
- Required primary keys, FKs, unique constraints, and indexes.
- Required seed rows.
- Validation failure blocks runtime startup.

## Table Deployment Order

1. `companies`
   - Root tenant table. Most operational tables reference `companies.key`.
2. `branches`
   - Depends on `companies`; required before branch-scoped users, module grants, POS, inventory movement, and document rows.
3. `users`
   - Depends on `companies` and optionally `branches`; required for auth/admin workflows.
4. `chart_of_accounts`
   - Self-references `parent_id`; create table first, then add self-FK if needed. Required before journals.
5. `customers` and `suppliers`
   - Depend on `companies`; required before invoices, bills, customer/supplier transactions.
6. `inventory`
   - Depends on `companies`; required before stock movements, invoice lines, POS lines.
7. Documents
   - `invoices`, `bills`, `invoice_lines`, `bill_lines`, `payments`, `payment_allocations`, `bank_accounts`, `recurring_transactions`, `accounting_periods`, `transactions`, `vouchers`.
   - Parent headers before line/allocation tables.
8. Journals
   - `journal_entries` before `journal_lines`; add indexes for company/date/source/customer/supplier lookups.
9. POS
   - `cashier_closings`, `pos_sales`, `pos_sale_lines`, `pos_returns`, `pos_suspended_sales`.
   - `pos_sales` before `pos_sale_lines`; POS tables depend on companies and optionally inventory/customer references.
10. Payroll and assets
    - `payroll`, `payroll_records`, `fixed_assets`; depend mainly on `companies` and optional supplier/journal references.
11. Audit, logging, licensing, and system tables
    - `audit_logs`, `system_logs`, `system_settings`, `maintenance_settings`, `pending_approvals`, `company_subscriptions`, `subscription_plan_settings`, `license_payment_transactions`, `database_identity`, `schema_version`, `migration_history`, `migration_logs`, branch licensing tables.
    - Branch licensing seed tables can be created early after `companies`/`branches`, but seed deployment should run after constraints exist.

## Validation Plan

After PostgreSQL schema deployment, run read-only validation against the staging database:

| Validation Area | Required Check |
|---|---|
| Table count | Confirm all source-of-truth tables plus compatibility/system tables exist; target should cover the current 51-table inventory unless compatibility exclusions are explicitly approved. |
| Column count | Compare required columns from the manifest against `information_schema.columns`. |
| Type mapping | Verify identity, boolean, money, date, timestamp, and FK column types match the PostgreSQL manifest. |
| Primary keys | Confirm every table has the expected primary key. |
| Foreign keys | Confirm child/parent mappings, delete behavior, and nullable optional references. |
| Unique constraints | Confirm business uniqueness constraints and partial unique account-code index. |
| Required indexes | Confirm company/branch/date/source indexes and FK support indexes. |
| Seed rows | Confirm `system_settings`, IFRS chart accounts, branch type catalog, branch module defaults, and subscription plan settings where required. |
| Branch type catalog | Expected branch types: retail, warehouse, main, subsidiary_main, office, other. |
| Module grants | Confirm default module templates and branch grant uniqueness constraint. |
| Journal tables | Confirm `journal_entries`, `journal_lines`, source-document indexes, and FK to chart of accounts. |
| POS tables | Confirm sales, lines, returns, suspended sales, cashier closings, uniqueness and lookup indexes. |
| Inventory tables | Confirm `inventory`, `inventory_import_batches`, `stock_movements`, FK/index coverage. |
| Migration metadata | Confirm PostgreSQL-native `schema_version`, `migration_history`, `migration_logs`, and recorded deploy version. |
| Runtime gate | Confirm PostgreSQL startup remains blocked until validation passes and a future phase explicitly relaxes the gate. |

## Cutover Status

The plan exists, but PostgreSQL schema deployment is not implemented. Cutover remains **NO-GO**.

Do not enable `ERP_ENABLE_POSTGRES_RUNTIME=1` in production. Do not deploy schema to Supabase until the staged deployer, schema validation, and SQL portability work are complete.
